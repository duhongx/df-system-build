# 当前 Vue 构建与更新流程

核对日期：2026-10-15。本文说明本轮代码的执行行为；目标约定见[前端更新规则](frontend-update-rules.md)。验证范围和线上激活情况见[实施与验收记录](frontend-update-implementation.md)。

## 应用登记与输入

| 角色 | 制品 | 发布目标 | 更新范围 |
|---|---|---|---|
| main | web-main.zip | web-main | 根目录，排除 apps |
| sub | appCode.zip | web-main | apps/appCode |
| cdn | web-cdn.zip | web-main | apps/cdn |
| standalone | 应用名.zip | 应用同名 Deployment | 独立站点根目录 |

仅 web-main 可以登记为 main，仅 web-cdn 可以登记为 cdn。子编号按字符串保存，保留前导零，允许小写字母、数字、下划线和短横线，最长 20 位；cdn 为保留名。登记和编辑均验证身份，数据库唯一索引覆盖启用、停用的子编号。有流水线历史后不能直接修改类型、角色或编号。

纯制品应用不要求 Git；源码任务仍要求真实仓库。本地环境允许源码构建，其他环境只允许制品更新。新增子应用发布时自动创建目录；若基线已有同编号目录，需有该应用的成功发布记录，或明确勾选“接管已核对的线上同编号目录”。迁移版本 6 为既有登记保留接管状态。应用登记不会写入业务门户菜单、权限或微前端配置。

ZIP 必须完整读取并通过 CRC 检查；拒绝重复、越界、绝对路径、链接和特殊文件，限制 100000 项、展开大小 4 GiB。业务包支持根 index.html 或单一 dist 根；两套入口或 dist 外额外内容存在歧义时拒绝。CDN 包不要求 index.html。

提交前检查登记、停用状态、标准制品名、入口脚本及本地引用。共享组重复来源、包内身份冲突等错误不消耗该组制品。通过预检查后按目标原子登记使用记录；后续失败、取消、回滚不重新开放原上传，再次更新需要新的上传版本。

## 常规主包与整包

源码主应用打包排除整个 apps。常规离线主包不得携带 apps，包括不完整目录；不会根据“有 index.html”自动增加更新范围。

确需整包联合发布时，包根增加 `.df-release.json`，声明主应用和每一个内嵌区域，例如：

```json
{
  "mode": "bundle",
  "regions": [
    {"role": "main", "appName": "web-main"},
    {"role": "sub", "appName": "web-menzhenysz", "appCode": "04"},
    {"role": "cdn", "appName": "web-cdn"}
  ]
}
```

每项必须对应已登记且启用的应用，声明目录必须实际提供；未声明的目录或与独立 ZIP 重复的区域拒绝。确认弹窗列出内嵌区域，部署记录按区域保存。清单不提供卸载语义，未出现的线上区域继续保留。

## 多个前端一起更新

“新增更新任务”一次选择多个子包（例如 04.zip、10.zip、12.zip），会合并成一个共享 Pipeline，固定全部输入，从 web-main 导出一份基线，在同一输出中分别清空并替换三个子目录，生成一个正式镜像。可以同时加入主包和显式 CDN 包；未选内容原样保留。独立应用仍是各自的 Pipeline 和 Deployment，不属于共享目标的成败事务。

已识别共享应用的包损坏、重复选择、身份或整包范围冲突，会阻断整个共享组；正式镜像构建或推送失败不会提交正式镜像。发布使用共享目标锁，提交前核对基线；手动等待期间目标改变则要求重新制作镜像。一次组合发布仍可能有 C、F 两次滚动，并非所有副本在同一时刻切换；已提交的阶段失败不会自动撤销。

“任务列表”的源码批量执行入口不同：逐个 CreateAndEnqueue，每个应用各自拉代码、编译和发布。共享目标锁将整条执行串行化，下一条使用与当时线上版本匹配的本地完整目录，失效时重新同步 Pod；不增加“全部编译成功后再统一合并发布”的批次协调。一个源码任务失败不会阻止其他任务，也不等同于离线多包的组合发布。

审计发现的边界：Execute 中若某项应用 ID 已不存在，入口先记录错误并跳过，无法识别其共享角色，剩余共享包可能继续创建发布；不能将当前行为宣称为所有异常选择都严格阻断共享组。

## 构建与目录替换

所有 Vue 角色走同一个受保护的镜像组装流程。源码输出 `.df-build.json`，记录实际应用、角色、编号、提交和文件摘要；读取时核对。遗留离线包可以没有这个文件，但仍固定输入 SHA256、应用绑定及组装清单。config.json 的 xiTongId 存在时按登记编号核对；gymk 可缺少该字段，opm 可没有 config.json。

非本地环境构建前读取当前 Deployment 的稳定 Ready 副本，核对 ReplicaSet 归属、容器、镜像和状态，导出 `/usr/share/nginx/html`。记录目标集群、namespace、UID、generation、镜像、ConfigMap resourceVersion 及内容摘要；导出完成后复核来源没有改变。独立应用读取自己的基线。本地环境使用下面的持久完整目录机制。

未选择的子目录、CDN、未知目录和空 60 目录不要求 index.html，原样保留并比较摘要。本次选择的业务包仍要求有效入口。整个 web-main 不存在时，不能只用子包初始化共享站点。

组装先复制完整基线，再清空所选业务区域并写入完整新包：主应用清空根目录除 apps 外的全部文件和目录；子应用清空 apps/编号；独立应用清空自己的整个站点根目录。包含隐藏文件、旧脚本和旧目录，新包未携带的内容不会留在正式镜像中；同路径业务资源允许替换。未选区域保持原样。CDN 保持单独的增量版本目录策略，同路径不同内容仍拒绝；主包或子包更新不清理 CDN。空间不足会在构建前停止。

所有操作发生在隔离工作区，输入和导出的基线不修改。镜像静态根清空后复制完整组装结果，避免基础镜像遗留页面混入。公共资源源码任务使用 cdn 目录，跳过 Vue 编译。

## 本地环境的持久完整目录

仅当环境配置 `customer_env` 为“本地”时启用。不增加额外开关，不复用 Jenkins 的 `/root/his-prod`，不停止 Jenkins，也不改变 Java 微服务流程。源码任务仍各自编译发布，同一共享目标串行执行；离线多包在本地运行时也使用同一个完整站点基础。

本地前端镜像使用与原 Python 模板一致的 `base/nginx:v2`；非本地继续使用已有的 `v1`，不把本地运行环境调整隐式带入客户环境。

目录位于后端工作区 `workspaces/frontend-sites/<目标摘要>/`，目标摘要由集群地址、namespace、Deployment 共同确定。`current.json` 指向一个 `site-*/html` 完整快照；web-main 的主应用、全部子应用和 CDN 共用一份，cdr、opm 及其他环境各自隔离。它是当前站点的构建基础，不是向正式镜像保留旧业务文件的策略。

第一次使用或目录失效时，从对应 Pod 导出并验证，保存当前完整站点。后续先核对 Deployment UID、generation、镜像、全部副本实际 ImageID 和挂载 ConfigMap 版本，再把保存的内容复制到本任务的隔离工作区，核对完整文件摘要。命中时不执行构建基线的 Pod 全目录导出；发布后的所有副本验证仍会读取 Pod。

在工作区按所选范围清空、写入新包、制作并发布镜像。只有正式镜像全部副本验证通过且发布记录已保存后，才把完整组装结果保存为新的当前目录。先写新快照并校验，再复核线上身份，最后原子替换 current.json；失败构建、仅制作镜像和 C 阶段不推进目录。正常替换后删除上一份本地快照，不把它当历史资源仓库。

Jenkins、人工发布、回滚、重建 Deployment、修改 ConfigMap 或同标签实际镜像变化，都会使保存记录与线上不匹配，下一条任务重新同步。同步前后均核对线上身份。若发布成功后目录保存失败，日志明确说明，保留已发布成功的事实，下次重新核对并同步。非本地环境直接走 Pod 导出，不读取或更新本地持久目录。

该机制以容器站点来自镜像为前提；不把“镜像未变”等同于对容器内人工热改文件的检测。Jenkins 与新系统仍是独立发布入口，不共享构建目录和进程锁；线上身份与提交版本检查用于发现冲突，不能使两个入口自动成为一个发布事务。

## 两阶段发布

已有站点先制作资源镜像 C，再制作正式镜像 F。C 临时保留基线入口和配置，预放本次新增静态资源；F 的所选业务区域严格使用新包，不包含该区域已删除的旧文件。两个镜像使用不同标签，推送后确认仓库 digest，部署使用不可变 digest 引用。C 仅为发布过渡，不是正式镜像的旧文件保留策略。

首次安装直接使用 F；没有新增资源或 C 已等于 F 时不执行多余阶段。仅制作镜像不会改变 Deployment。本地环境推送成功后自动继续，其他环境停在 IMAGE_READY，人工提交后使用同一份镜像和基线发布。

发布前重新核对登记、停用状态、基线和 ConfigMap 版本。已有站点只修改镜像和发布归属注解，不自动修改 Nginx、Service、Ingress、挂载、探针或副本。每个提交使用读取到的 resourceVersion；已登记的 B→C→F 变化会逐阶段保存，外部变化会被拒绝。

C 的全部副本完成滚动及技术验证后，才能提交 F。最终按所有副本重新导出站点比较完整摘要，验证所选入口、脚本、样式、子应用深层路由及缺失 JS 的 404 行为。删除的旧业务资源不再要求可访问。旧页面在更新后请求已删除资源可能失败，需要刷新；同路径内容变化也不承诺新旧页面兼容。版本信息可选采集；它不能代替文件和 HTTP 校验。业务门户、权限和业务功能需单独验收。

阶段进度包括 assets_submitting、assets_submitted、assets_ready、submitting、submitted、verifying、completed。失败停止后续动作，不自动回滚；取消不撤销已被 Kubernetes 接受的操作。发布完成但数据库保存失败按实际事实记录，不显示为未部署。

## 回滚

同一目标的构建、发布、回滚使用同一进程锁，独立应用各自锁定。当前为单后端实例，不具备跨实例锁。

回滚前核对后续发布记录、当前镜像、发布归属、UID、generation 和 ConfigMap 版本。较早批次不能覆盖后续更新。已验证的 C 优先作为兼容恢复镜像，保留新客户端所需资源；回滚后再次等待全部副本并核对完整文件摘要及入口。

共享回滚恢复整个 web-main；只回退某个子应用需要重新上传指定历史子包，基于当前基线创建新更新任务。当前没有专门的“选择历史子版本定向回退”页面。独立应用回滚不改变共享目标或其他独立站点。

## 现网配置边界

代码更新不会悄悄替换生产 Nginx。新的默认模板修复子应用深层路由、静态 404 及缓存头，但既有 ConfigMap 和数据库中的自定义模板仍需通过明确的配置变更处理，保留 API 代理等环境配置。现有错误配置会被 HTTP 验证识别，不能视为发布成功。

旧 IMAGE_READY 任务若缺少新文件清单或两阶段信息，需要重新制作镜像。自动资源回收、跨实例互斥、环境字段合成、不兼容固定配置的维护窗口发布和专用历史子版本回退页面仍未提供，不能按已有能力使用。
