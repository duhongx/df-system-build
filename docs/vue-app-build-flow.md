# 前端微服务更新流程与故障处理

核对日期：2026-09-09。依据当前工作区代码，包含本轮已实现的 web-main 更新改造。本文描述“目前会怎样执行”，人工处理步骤是操作建议，不代表已经实现自动恢复。真实集群发布／回滚尚未验收。

适用前提：每个环境独立部署本系统，业务系统由单人操作更新；一次可以选择多个应用；运行单个后端实例。本文以“更新版本中选择已有 ZIP 制品并发布”为主，源码构建的前置阶段见文末。

## 1. 先区分实际更新目标

| 选择的应用 | 应用角色 | 输入制品 | 最终镜像／Deployment | 一次请求内的流水线数量 |
|---|---|---|---|---|
| 一个子应用，例如 appCode=04 | `vue/sub` | `04.zip` | `web-main` | 1 |
| 多个子应用，例如 04、05 | `vue/sub` | `04.zip`、`05.zip` | `web-main` | 合并为 1 |
| 主应用 | `vue/main` | `web-main.zip` | `web-main` | 1 |
| 主应用和多个子应用 | `vue/main` + `vue/sub` | 主包和子包 | `web-main` | 合并为 1 |
| web-cdr | `vue/standalone` | `web-cdr.zip` | `web-cdr` | 1 |
| web-opm | `vue/standalone` | `web-opm.zip` | `web-opm` | 1 |
| 主／子应用 + web-cdr + web-opm | 混合 | 对应 ZIP | 三个 Deployment | 3，分别执行 |

web-cdr 和 web-opm 的独立角色来自应用初始化和迁移规则，执行仍以实际应用配置为准。

**子应用更新的文件范围是局部，但发布和回滚的单位是整个 web-main 镜像与 Deployment。** 更新 04 不会创建独立的 04 Deployment，却会使 web-main 的 Pod 滚动替换。没有“只重启 04 文件目录”的操作。

代码依据：[应用角色](../backend/internal/repository/seed_apps.go)、[迁移规则](../backend/internal/repository/migrations.go)、[批量任务分组](../backend/internal/handler/batch_deploy.go)。

## 2. 提交更新之前

1. 在更新版本中准备 ZIP，确认文件与应用匹配，选择目标 namespace。
2. 执行第一步“上传并制作镜像”；制作并推送完成后，再执行第二步“滚动更新”。
3. 页面按实际应用角色分别列出独立应用与 web-main 合并组，并展示主应用、子应用和制品名称，确认后提交。仅选择 web-cdr／web-opm 时不会提示合并到 web-main。当前弹窗不是从集群读取的逐子应用版本差异预览；实际替换／保留目录会在组装日志列出。
4. 后端检查来源目录、文件存在性、非空、基本 ZIP 格式、应用匹配及重复选择。
5. 制品校验、SHA-256 计算和工作区复制统一解析实际文件路径，支持下载目录下嵌套的 ZIP。按部署目标检查制品：某个独立服务校验失败，跳过该服务；主应用或所选子应用校验失败，跳过整个共享 web-main 组；其他有效目标继续创建任务。来源目录、请求参数错误仍拒绝请求；应用无法识别时记录该项错误，其他可识别目标继续。基本 ZIP 检查不等于完整解压，深层错误可能到构建阶段才发现。
6. 将同批主／子应用归入一个任务；web-cdr、web-opm 分别创建任务。主／子任务保存所选文件名、角色、appCode 和 SHA-256，执行时不从当前应用目录猜测本次要更新哪些包。
7. 按部署目标分别在事务中检查并记录所选制品已提交更新，然后创建流水线和部署记录，将选中制品复制到该流水线独立工作区，最后入队。已使用制品不再创建流水线，不影响其他目标提交。

第 7 步按目标独立执行：某个任务复制文件或创建记录失败，记录该任务失败并跳过，继续处理其他目标。已入队任务在构建、推送、滚动更新中失败时，只停止该任务后续阶段；调度器继续执行其他任务。页面展示已创建任务数量及逐项错误，准备阶段失败原因同时保存到流水线和部署记录。部署记录先于工作目录创建和制品复制写入，复制失败仍计入批次失败数量。失败任务保持 FAILED，不将“跳过”标成成功，也不触发自动回滚。

### 制品只能更新一次

使用次数按“上传版本号 + 文件名”记录。一份制品提交更新后，立即标记为“已提交更新”，不能再次勾选；全部可部署制品已使用时，更新按钮禁用。未选中的制品仍可使用。后端也会拒绝重复提交，刷新页面或重新扫描工作区不会清除此状态。

使用记录在对应部署目标的输入预检查通过后、创建任务之前保存，各目标分别提交；共享 web-main 组内一起提交。此后即使创建任务、复制文件、构建或部署失败，或者执行取消／回滚，原制品也不会重新开放；再次更新必须重新上传。输入预检查失败则没有消耗制品。滚动更新使用同一次镜像制作的结果，不重复消耗制品。

再次上传同名、同内容的文件会生成新的版本号，因此可以更新。已有部署记录的旧制品也视为已使用；已使用制品不允许原地替换、删除或重下载来重置状态。使用记录独立保存于 `artifact_update_claims`，启动时自动建表。

## 3. 统一阶段与状态

制品直接发布只有四个可见阶段：

`BUILD_IMAGE → PUSH_IMAGE → K8S_DEPLOY → NOTIFY`

ZIP 校验、Pod 导出和目录组装都属于 BUILD_IMAGE；资源创建、滚动等待和展示用版本信息采集都属于 K8S_DEPLOY，不一定在页面上显示为独立阶段。

### 第一步：上传并制作镜像

`PENDING → RUNNING → IMAGE_READY / FAILED / CANCELED`

上传、匹配和检查制品，创建更新记录，按目标制作并推送镜像。推送完成后第一步结束，保存镜像 tag、阶段结果、结束时间和耗时；不会执行 Kubernetes 更新。IMAGE_READY 在页面显示为“镜像制作完成”。某个目标失败后停止该目标，其他目标继续。

### 第二步：滚动更新

`IMAGE_READY → DEPLOYING（排队）→ RUNNING → SUCCESS / FAILED / CANCELED`

- 在更新版本详情、任务详情、更新记录列表或构建队列中点击“滚动更新”。
- 单目标接口为 `POST /api/pipelines/:id/rollout`；批次接口为 `POST /api/batch-deploy/deploy-batches/:batchNo/rollout`。
- 第二步使用第一步保存的镜像和已完成阶段，只执行 K8S_DEPLOY、NOTIFY，不重新制作或推送镜像、不再次消耗制品。
- 镜像制作结果不完整、推送失败、状态不符时明确报错；同一任务不能重复提交滚动更新。
- 批次只提交当前 IMAGE_READY 的流水线；主／子应用共用的一条流水线只提交一次。部分镜像制作失败的批次仍能更新成功制作的镜像，某个目标提交失败也继续其他目标。
- 第一阶段制作成功不会自动取消其他任务已制作的镜像。web-main 部署前仍检查制作时的基线，避免组装镜像覆盖之后已更新的目录。
- 第二步可在第一步 worker 退出前提交，调度器会等原 worker 退出后执行，确保复用同一组阶段。

代码依据：[阶段定义](../backend/internal/pipeline/stage_resolver.go)、[执行引擎](../backend/internal/pipeline/engine.go)、[滚动更新提交](../backend/internal/scheduler/rollout.go)、[批次入口](../backend/internal/handler/batch_deploy.go)。

## 4. 单个子应用更新

以 `04.zip` 更新 `apps/04` 为例，线上有主应用 M1、04=A1、05=B1。

### BUILD_IMAGE：准备完整新镜像

1. 读取该任务固定的制品清单，只处理 04.zip。
2. 重新计算 SHA-256，与提交时保存的值比较。
3. 解压到隔离目录，接受 `index.html` 位于包根目录或顶层 `dist/` 的结构。要求 index.html 是普通文件。
4. 查询当前 namespace 的 web-main Deployment；查询异常立即失败。Deployment 不存在时，子应用单独更新失败。
5. 确认 Deployment 当前版本已经完成滚动更新、副本数大于 0，再按 selector 和 ReplicaSet 归属选择 Pod。目标 web-main 容器必须 Ready，镜像必须与 Deployment 当前镜像一致，Pod 不能处于删除中。
6. 导出该 Pod 的 `/usr/share/nginx/html` 到临时目录。传输与解压必须成功；检查根 index.html 和现有 apps/ 下各子目录的 index.html。
7. 在新的组装目录复制完整基线，清空其中 `apps/04`，复制本次子包。线上 Pod 和导出的基线目录不会被这些本地替换操作修改。
8. 保留主应用、apps/05 和所有未选择的线上子应用，包括未登记在当前应用配置中的子应用。
9. 检查组装结果，构建新的 web-main 镜像。镜像标签带流水线 ID，构建基线与镜像名称一起保存。

预期内容变化：

| 区域 | 更新前 | 更新后 |
|---|---|---|
| 主应用 | M1 | M1 |
| apps/04 | A1 | A2，旧目录文件全部替换 |
| apps/05 | B1 | B1 |

### PUSH_IMAGE 与 K8S_DEPLOY

推送新镜像后第一步完成；第二步由“滚动更新”操作提交。部署时重新检查 web-main 基线，更新整个 Deployment，等待指定镜像滚动完成、应用就绪，即完成部署。版本信息仅采集展示，不参与成功判定。

所以“只更新子应用”不会改变其他应用的预期文件内容，但仍涉及整个 web-main Pod 的滚动、共享 Nginx 进程和入口流量。是否无中断取决于实际副本、滚动策略、探针及客户端资源缓存，当前代码不能仅凭选择一个子应用保证零中断。

## 5. 单个 web-main 更新

### 主包只包含主应用

前面的清单、哈希、ZIP 和线上基线检查与子应用相同。组装时：

1. 复制新主应用根目录到新的组装目录。
2. 使用线上基线的完整 apps/ 树保留现有子应用。
3. 删除的旧根目录文件不会自动保留，例如旧主应用 JS/CSS。
4. 构建、推送和滚动更新 web-main。

例如 `M1 + A1 + B1` 变成 `M2 + A1 + B1`。

### 主包同时包含子应用

如果 web-main.zip 内存在 `apps/04/index.html`，会将 apps/04 识别为本次要替换的完整子应用目录。选择“一个 web-main.zip”并不必然只更新主应用。

例如主包含 M2 和 A2，线上是 `M1 + A1 + B1`，结果为 `M2 + A2 + B1`。如果同时独立上传 04.zip，会因为重复提供子应用而失败。

主包中没有有效 index.html 的子目录不会被识别为完整内嵌子应用。有现有 apps/ 基线时，组装会恢复基线的 apps/，这种碎片不会替换旧子应用。首次部署没有基线时，最终目录中缺少入口的子目录会使完整性检查失败。

因此发布前需要检查主包内部，不能仅看文件名判断替换范围。

### 首次部署

只有查询明确返回 Deployment 不存在时才进入首次部署；网络错误、权限错误、没有 Ready Pod、导出失败都不会降级成首次部署。

首次部署至少提供有效的主应用 ZIP，可以同时携带内嵌或独立子应用包，所有选中子包都必须成功组装。当前没有“每个 namespace 必须安装哪些子应用”的清单模型，因此不会强制安装全局配置里的所有子应用。

如果 Deployment 已存在但当前前端内容不完整，即使上传一份完整新包，当前路径也会先因基线检查失败而停止。需要先核实并恢复可用基线，或通过受控的完整镜像部署修复现网，不能靠把读取错误当作首次部署来绕过。

代码依据：[制品与目录组装](../backend/internal/pipeline/stages/web_update.go)、[Pod 读取和基线检查](../backend/internal/pipeline/stages/web_runtime.go)。

## 6. 多个子应用更新

例如一次选择 04.zip 和 05.zip：

1. 合并为一条 web-main 流水线，保存两份明确的制品引用与哈希。
2. 两个包都先解压并验证；其中任何一个缺失、损坏、校验和改变或 appCode 无效，整个前端任务失败。
3. 一次导出当前完整前端基线。
4. 在本地组装目录分别完整替换 apps/04 和 apps/05，保留主应用及其他子应用。
5. 所有目录检查成功后，只构建、推送一个镜像，只执行一次 Deployment 更新。
6. 滚动完成后记录部署成功；两个子应用的版本信息仅用于展示。

例如 `M1 + A1 + B1 + C1` 变成 `M1 + A2 + B2 + C1`。

如果替换第二个子应用时复制失败，本地临时目录可能已经处理了一部分，但该组装结果不会进入后续镜像推送和部署。线上仍是原版本。

主应用和多个子应用一起更新同理，只是同时替换主应用根目录。组装是发布前的全组检查；实际 Pod 滚动期间仍会短暂存在旧镜像和新镜像副本，不构成所有客户端同时切换的事务。

## 7. 单个 web-cdr / web-opm 更新

这两个应用属于 standalone，当前仍走标准镜像流程，与共享 web-main 的增强路径不同。

以 web-cdr.zip 为例：

1. 匹配 web-cdr 应用，创建独立流水线和工作区。
2. 读取 `dockerfile-web` 配置项，解压 ZIP 到 `docker-build/dist`。
3. 使用该模板构建 `registry/web-cdr:branch-time-p流水线ID`，仅推送本次唯一版本标签，不制作或推送 latest 标签。
4. 第一步制作并推送镜像完成后，通过第二步滚动更新 web-cdr Deployment。
5. 按配置处理 `configmap-web-cdr`、Service 和 Ingress。
6. 等待滚动完成、应用就绪，保存结果；版本信息采集失败不改变成功状态。

web-opm 对应 web-opm.zip、web-opm 镜像／Deployment、configmap-web-opm，其他步骤相同。两者不会读取或合并 web-main 的文件，不影响其预期文件内容。

### ZIP 目录层级统一处理

独立应用与主／子应用统一使用目录规范化逻辑：ZIP 中根目录的 `index.html` 或顶层 `dist/index.html` 都会落到 `docker-build/dist/index.html`。只有解压和入口检查通过，才用新目录替换原本地制品目录，旧文件不会混入新包。

内置 Dockerfile 的 `COPY dist /usr/share/nginx/html` 因而能将入口复制到 `/usr/share/nginx/html/index.html`。业务环境自定义 Dockerfile 仍需与该构建目录约定一致。

### 独立应用当前没有的保护

- 没有主／子应用这套提交清单 SHA-256 重校验、构建基线及过期基线拦截。
- 没有发布后的完整文件树摘要对比。
- 更新已有 Deployment 时仍使用镜像 Patch；不具备共享 web-main 的构建基线条件检查。

这些是当前实现边界，不能把所有前端应用描述为已经具有相同的发布保护。

代码依据：[标准镜像分支](../backend/internal/pipeline/stages/build_image.go)、[内置 Dockerfile](../backend/internal/repository/seed_config_items.go)、[源码 ZIP 打包](../backend/internal/pipeline/stages/zip_package.go)。

## 8. 镜像推送与滚动更新的详细顺序

### PUSH_IMAGE

推送本次版本镜像；该推送返回失败则停止，不进入 Kubernetes 部署。本地可能留下镜像，仓库可能已有上传的层，线上 Deployment 尚未由本次任务改变。

构建响应正常结束后会检查目标镜像标签。推送要求收到完成 digest，并通过 Docker Distribution API 确认仓库 digest 一致；响应截断、读取异常、镜像缺失或无法确认都会停止。不制作或推送 branch-latest 等辅助标签。Deployment 当前仍使用本次版本标签，没有改为 digest 引用。

### 滚动更新前的基线检查（仅共享 web-main）

构建时保存目标集群地址、namespace、Deployment 是否存在、UID、generation、旧镜像、新镜像。

确认后重新核对；任何不一致都会停止并要求重新构建。例如同一人先构建 04 的待发布镜像，又发布了 05，再确认旧的 04 镜像，旧任务会被拦截，以免把 05 覆盖回旧版本。这与是否存在多个人同时更新无关。

镜像制作完成后释放 web-main 互斥，滚动更新时重新获取。升级之前创建、缺少新清单或基线的前端制品任务需要重新上传后提交。

### K8S_DEPLOY 内部顺序

1. 获取 K8s 客户端、确认 namespace 和 Deployment 目标。
2. 共享 web-main 校验构建基线。
3. 读取更新前目标镜像及滚动状态，保存可回滚镜像与更新前目标镜像，尝试读取更新前业务版本。
4. 处理 ConfigMap。
5. 更新或创建 Deployment。
6. 处理 Service。
7. 处理 Ingress。
8. 等待 Deployment 滚动更新。
9. 记录指定镜像滚动完成的结果，不再二次导出线上静态目录。
10. 按部署记录采集版本信息，仅用于展示，不比较或决定更新结果。每次采集最多等待 3 秒，错误保存到独立的 versionWarning 提示并输出服务端日志。

共享 web-main 更新已有 Deployment 时使用读取到的 resourceVersion 提交，遇到资源冲突失败，不强行覆盖。

主应用和独立应用处理 Service／ConfigMap／Ingress；子应用只更新共享 Deployment。资源已存在时一般跳过，不同步覆盖线上配置。Vue 当前最多使用第一条 Ingress 配置。

**资源操作不是事务，而且 Deployment 先于 Service／Ingress 操作。** 因此 Service 或 Ingress 处理失败时，镜像可能已经更新；首次部署失败也可能留下已创建的部分资源，没有自动删除或还原。

制作和推送镜像时，镜像仓库地址是必填配置。仓库认证、Nacos 和 SkyWalking 的可选配置不存在时保留空值行为；数据库读取失败则停止当前任务，报告配置项名称和原始错误，不输出凭据值。Dockerfile 模板不存在、为空和查询失败分别报错。

### 滚动完成与版本信息

- 滚动等待上限为 300 秒，也受整条流水线超时限制；调度器默认任务超时为 30 分钟，可由设置覆盖。
- 检查 controller 已观察到目标 generation，副本总数、更新数、Ready 数、Available 数与期望一致，Unavailable 为 0。
- Deployment 失败条件和已识别的 ImagePullBackOff、ErrImagePull、CrashLoopBackOff、CreateContainerConfigError 会使等待失败；查询错误会保留原因并停止。Pod 检查按 Deployment selector、所有权与当前模板匹配 ReplicaSet，忽略旧版本、其他 Deployment 和正在删除的 Pod。
- 共享 web-main 文件校验比较所选一个 Ready Pod 的文件相对路径和内容。它不检查所有副本，不比较文件时间／权限／空目录，也不替代浏览器和业务接口检查。
- 滚动失败或超时时，附加本次新 ReplicaSet 所属 Pod 的状态、容器退出码及退出原因、当前／上次退出日志和 Pod 事件。采集总时限 10 秒，最多 3 个 Pod、每个最多 3 个容器，每段日志最多 50 行／4 KiB，总输出最多 32 KiB；权限不足或采集失败会说明原因，始终保留原始更新错误，不改变集群。
- 如果滚动已完成而后续记录保存失败，流水线列表、详情、制品部署明细及通知会区分“部署成功，结果记录异常”和真实部署失败。底层任务仍记录异常，已知部署成功状态不会被改成启动失败；数据库不可写时实时提示保存错误，持久化状态可能尚未更新。
- 现有业务版本文件：主应用和独立应用读取 `/usr/share/nginx/html/config.json`；子应用读取 `/usr/share/nginx/html/apps/{appCode}/config.json`。
- 更新前镜像读取或部署记录保存失败会停止当前任务；版本信息读取失败只记录提示。ConfigMap 查询、模板读取、解析或创建失败也会停止，不再按独立应用可选项吞掉错误。已存在的 ConfigMap 仍按原行为跳过，不自动覆盖。
- 更新前后版本只采集展示，不作强制比较；采集失败不阻止更新，不将已完成的滚动更新标记为失败。没有对应部署记录时不采集。
- 主包内嵌的子应用会参与完整文件校验，但不会自动生成一条独立的选中制品部署记录。

## 9. 每个阶段出错时怎么处理

下表的“系统行为”指当前代码。人工处理应以实际日志、Deployment、Pod 和镜像为依据，不能只看汇总状态。

| 出错位置 | 系统行为 | 线上可能状态 | 人工处理 |
|---|---|---|---|
| 选择、匹配、基本制品校验 | 对已识别目标按组跳过失败输入，其他目标继续；无法识别的应用单独跳过 | 失败组未被本次请求修改 | 按具体错误修复并重新上传 |
| 创建任务、复制输入、建立部署记录 | 对应任务不入队或标记失败；其他已入队任务可能继续 | 该失败任务通常未部署；其他任务需分别检查 | 检查磁盘、源文件和数据库；先核对本批已启动任务再补交失败项 |
| 排队、等待共享目标互斥 | 等待；取消／超时后停止 | 尚未提交部署的任务不改变线上 | 等已有任务结束；检查是否设置了过短超时 |
| 读取清单、SHA-256 检查 | 当前任务失败，后续阶段跳过 | 旧版本 | 恢复制品或重新选择正确版本；不要修改清单绕过校验 |
| ZIP 解压、index.html／路径检查 | 前端任务失败；不发布部分内容 | 旧版本 | 重新提供完整 ZIP；核对根目录或 dist 层级 |
| 读取 Deployment／Pod／ReplicaSet | 主／子任务失败，异常不当作首次部署 | 旧版本或之前遗留的异常状态 | 检查 K8s 连接、权限、副本、当前 rollout；恢复可信基线后重提 |
| Pod 导出、tar 解压、基线内容检查 | 丢弃临时导出，停止更新 | 旧版本或原有异常状态 | 查 tar、exec 权限、网络、磁盘及入口文件；不能用空基线继续 |
| 目录组装、复制 | 当前前端任务整体失败 | 旧版本 | 修复制品或磁盘问题；重新上传并提交，不继续使用半成品目录 |
| Docker 镜像构建 | 返回错误后停止，PUSH_IMAGE／K8S_DEPLOY 跳过 | 旧版本 | 查 Docker、基础镜像、模板、空间和构建日志 |
| 正式镜像推送 | 返回错误后停止 | 旧版本；仓库可能有部分层 | 修复仓库连接、权限、存储；重新上传后创建新任务 |
| IMAGE_READY 镜像制作完成 | 第一步已完成，尚未更新 Deployment | 旧版本 | 执行第二步滚动更新；不再需要则取消任务 |
| 确认重复、阶段不完整 | 拒绝确认或恢复失败，不重新构建 | 本任务尚未提交部署 | 刷新状态；不完整旧任务重新上传后提交 |
| 共享 web-main 基线已变化 | 部署前失败，不覆盖新基线 | 当前较新的线上版本 | 基于当前线上重新构建，再确认 |
| 更新前镜像／记录处理 | 当前任务返回错误后停止，其他任务继续 | 尚未提交本次 Deployment 更新 | 查镜像读取、K8s 权限与数据库错误；展示版本采集失败不阻止更新 |
| ConfigMap 处理 | 返回错误后停止，不吞掉独立应用错误 | Deployment 尚未提交，配置资源可能已经创建 | 查原始查询、模板、权限或创建错误 |
| Deployment Update／Create 请求失败或超时 | 当前阶段失败，没有自动回滚 | 可能未变化，也可能服务端已接受 | 先读取实际镜像、generation、Pod；确定原因并修复后重新上传更新 |
| Service／Ingress 处理失败 | 部署阶段失败，后续检查停止 | Deployment 可能已经更新 | 查新镜像和入口资源，选择修复入口后重新上传更新 |
| 滚动失败／超时 | 阶段和任务失败；没有自动回滚 | 可能是旧副本、新副本或混合状态 | 查拉镜像、启动日志、探针、配置和资源；修复后重新上传失败服务的制品更新 |
| 版本信息采集失败 | 仅记录提示，不阻止部署或回滚 | 以镜像滚动结果为准 | 查看版本信息提示；不因采集失败重新发布 |
| 最终状态／批次汇总写数据库失败 | 返回或报告原始错误；流水线详情实时显示保存失败，停止普通完成通知 | 已执行的集群操作不会撤销 | 排查数据库错误，核对执行日志与集群；页面持久化状态可能仍旧 |
| NOTIFY／外部通知失败 | NOTIFY 是展示阶段；实际通知由调度器异步发送 | 不因通知失败恢复旧镜像 | 查通知设置，按指定镜像滚动结果判断发布，不重发业务更新 |

只有在明确尚未进入集群写入阶段时，才可判断本任务没有修改线上。**FAILED、CANCELED、页面断线都不等于“旧版本已恢复”。**

## 10. 取消、页面断开和后端重启

| 情况 | 当前行为与处理 |
|---|---|
| 关闭浏览器、刷新页面、SSE 断线 | 已入队任务通常继续；重新打开队列和详情读取状态，不能把页面断线当作取消 |
| 取消排队任务 | 从队列移除并标记取消；尚未部署 |
| 取消正在构建／推送的任务 | 向执行上下文发送取消信号，外部操作退出可能有延迟；本地镜像或仓库层可能保留 |
| 取消已经提交 Deployment 的任务 | 停止本次后续执行／等待，不撤销 Kubernetes 已接受的变更；集群可能继续滚动 |
| 取消 IMAGE_READY 任务 | 不执行切换；已推送镜像不会因此自动删除 |
| 后端重启时任务是 PENDING／已确认待调度的 DEPLOYING | 启动后重新入队；恢复部署仍需通过已有阶段与基线检查 |
| 后端重启时任务是 RUNNING | 标记失败并保存中断原因、运行阶段日志和最后部署进度；不自动重放、核对集群或回滚，已提交更新需人工核实 |
| 后端重启时任务是 IMAGE_READY | 保留镜像制作结果；旧版本程序创建且缺少新基线的任务需要重新上传后提交 |

没有通用的失败阶段断点重试机制。除使用 IMAGE_READY 结果执行滚动更新外，失败后的常规处理是修复问题并创建新任务；若曾进入部署阶段，必须先确定线上结果。

## 11. 回滚怎么做、会恢复什么

当前提供手工触发的批次镜像回滚。部署中某个服务失败时，跳过失败任务、继续其他任务；排查并修复后，重新上传制品更新。整批回滚用于更新成功后发现计费失败、业务逻辑不符合预期等业务异常，由人工选择恢复业务，不作为部署失败的自动处理步骤。

1. 点击“整体回滚”提交后台任务，接口立即返回批次任务标识。浏览器请求结束、刷新或关闭页面不会中断回滚。
2. 服务端按 namespace／Deployment 分组，依次恢复记录的可回滚镜像；多个子应用只对 web-main 操作一次。每个目标最多等待 5 分钟，某个目标失败后继续其他目标，不自动撤销已成功的回滚。
3. 页面每 3 秒刷新进度，展示等待回滚、回滚中、成功、失败和详细错误。准备失败且未提交部署的目标标为“无需回滚”，保留原更新错误。
4. 所有需恢复的目标滚动完成、应用就绪后，批次才显示回滚完成。版本信息只采集展示；业务恢复效果由人员确认。
5. 后端进程重启会把未完成的回滚标为中断并保存原因，保留已完成目标；不自动重放集群操作。需按提示核对实际镜像和滚动状态，再由人员处理。

记录中的 `beforeDesiredImage` 是本次更新前 Deployment 配置的目标镜像，`beforeImage` 是供人工回滚使用的镜像。正常完成滚动时，两者相同。如果 A0 → A1 滚动失败，修复后重新上传部署 A2，更新前目标镜像为 A1，可回滚镜像沿用 A1 更新记录中的 A0；不会把启动失败的 A1 当作恢复目标。连续失败重试也沿用该记录。如果 A1 已实际完成滚动，则使用 A1。无法找到对应历史记录且当前滚动未完成时，不阻止新制品修复更新，但可回滚镜像留空并明确记录，不能伪造恢复标签。

| 原更新 | 镜像回滚实际范围 |
|---|---|
| 只更新 04 | 恢复整个 web-main 旧镜像，包括当时的主应用与所有子应用 |
| 同时更新 04、05 | 一次恢复整个 web-main 旧镜像 |
| 更新 web-main | 恢复整个 web-main 旧镜像 |
| 更新 web-cdr／web-opm | 恢复各自 Deployment 的旧镜像 |
| 批次涉及多个 Deployment | 分组逐个回滚，某组失败记录错误并继续其他组，最终汇总各组结果 |

恢复镜像不回滚数据库 SQL、业务数据、已经创建或修改的 Service／ConfigMap／Ingress。首次部署没有旧镜像时，现有批次回滚会因缺少可回滚镜像失败，不能依赖它自动删除首次资源。

当前仍以上传版本号关联部署批次，但同一制品不能再次提交；重新上传会生成新的版本号。按本项目使用流程，更新成功后出现业务异常、人工选择整批回滚时，恢复本次记录的可回滚镜像。

代码依据：[后台回滚任务](../backend/internal/service/artifact_rollback_job.go)、[回滚镜像记录](../backend/internal/service/deployment_before_image.go)、[回滚分组](../backend/internal/service/artifact_deploy_rollback.go)、[K8s 回滚](../backend/internal/service/artifact_runtime_k8s.go)、[部署记录](../backend/internal/service/artifact_deploy_record.go)。

## 12. 源码构建的前置阶段

从构建任务触发 Vue 更新时，镜像构建之前还有：

`CLEAN_WORKSPACE → GIT_CLONE → YARN_BUILD → ZIP_PACKAGE`

- 清理、Git 拉取、安装依赖／编译或 ZIP 打包返回错误时，停止后续镜像和部署阶段，线上尚未由本次任务修改。
- 当前 ZIP_PACKAGE 固定打包 source/dist，ZIP 内保留顶层 dist；主／子／独立前端镜像分支都会展平，见第 7 节。
- `upload_only` 只执行远端目录检查和制品上传，不更新 Kubernetes。
- `upload_and_build` 会先上传到远端再构建镜像（兼容旧配置 `upload_and_deploy`），上传已经完成而后续发布失败时，远端制品可能已经变化；它与只读 Pod 的制品发布路径不同。
- 源码主／子任务按该任务自己的包作为输入；批量选择多个已有子包更新应走制品批量更新入口。

## 13. 保护范围与验收标准

当前采用 namespace + web-main 的进程内互斥，覆盖构建、推送和部署；批次回滚对 web-main 的镜像操作也使用该互斥。不同 Deployment 仍按原有调度配置执行。这用于串行完成同目标任务，不是多人协作或跨实例分布式锁。

共享 web-main 的 ZIP／Pod 导出限制为 100000 项、4 GiB；拒绝越界路径、符号链接及 tar 特殊文件。目录导出用于构建前保留未更新的内容；滚动完成后不再导出目录进行摘要验证。

平台更新流程验收确认以下结果：

1. 第一步制作、推送的镜像与所选制品对应，前端拼装范围符合应用角色和清单。
2. 第一步结束后未提交 Deployment 更新；第二步使用已制作镜像，副本滚动完成并就绪。
3. 发布记录、各目标状态与实际部署一致，错误阶段和原因可查询；人工回滚使用记录的镜像。

业务功能和浏览器资源兼容性由业务开发与维护人员验证，不参与平台部署成功判定。

已完成本地目录替换、输入错误、基线失效、Pod 选择、tar 错误、重复提交滚动更新与数据库链路测试；真实 Docker／Kubernetes 和故障恢复尚未验收。验证记录见 [PROGRESS.md](../PROGRESS.md)。

## 14. 更新执行详情日志

流水线详情页按阶段展示历史日志和实时日志。新提交的制品批量更新会保存本批次选择的前端应用清单，在每条流水线首次执行的阶段打印：独立应用、主应用、子应用的名称、appCode 和制品文件。清单表示提交范围，不表示所有应用已经部署成功；独立应用仍由各自流水线执行。旧任务没有这份新快照时，只能打印已有任务信息和实际制品清单。

执行详情包括：

- **任务与阶段**：流水线、当前应用、命名空间、部署模式、是否执行第二步滚动更新，以及阶段开始、完成、失败和耗时。
- **制品准备**：共享前端 ZIP 的路径、大小、提交时 SHA256 校验、解压目录、识别出的站点根目录；主应用包内完整子应用的识别结果。不完整的内嵌子目录会明确记录为不作为完整替换来源。
- **运行目录复制**：当前 web-main Deployment 的 UID、generation、镜像，以及实际选中的 Pod、容器、tar 命令、线上来源目录和本地目标目录。复制完成后打印文件数和字节数。
- **目录组装**：清理本地镜像工作目录、复制主应用或完整基线、保留线上子应用、逐个清空本地待更新子应用目录、写入新制品，以及最终替换和保留清单。每个文件操作先打印开始，仅成功后打印完成；失败信息包含操作名称、来源、目标和原始错误。
- **独立应用**：当前应用、制品、独立 Deployment、解压路径与结果、Dockerfile 模板和路径。
- **镜像制作与上传**：提交给 Docker 的构建上下文目录、Dockerfile 路径、共享前端基础镜像、目标标签、Docker 原始构建输出和唯一镜像标签的推送输出。
- **部署与记录**：目标命名空间、Deployment、镜像、提交开始和 API 接受更新、滚动进度、应用就绪和结果保存。版本信息采集失败另行展示，不参与成功判定。

共享前端流程中的“清空”和“写入”作用于本地构建目录。运行中的 web-main 用于导出基线，制品通过构建镜像和推送镜像仓库发布，不会把 ZIP 直接上传到运行中的 Pod。日志中的路径会区分这些操作。

Pod 导出的 tar 诊断保留前 64 KiB，超出时标记截断。阶段失败时打印原始原因并停止后续步骤；部署阶段失败还会提示已提交的 Kubernetes 操作可能仍在执行，不能据此认定线上没有变化。

实时日志携带阶段 ID、数据库日志 ID 和 stdout/stderr 标记；历史查询与实时日志合并去重。页面会定时补取所选阶段日志，排队中的任务也会继续刷新。查看历史阶段时，新阶段日志不会追加到历史阶段中。

代码依据：[日志辅助](../backend/internal/pipeline/stages/web_log.go)、[阶段日志执行](../backend/internal/pipeline/engine.go)、[流水线详情页](../frontend/src/views/PipelineDetailView.vue)。

## 15. 更新错误处理修复（2026-09-09）

共享 web-main Dockerfile 在 COPY 前删除并重建镜像的 `/usr/share/nginx/html`，使最终静态目录与本地组装内容一致，避免基础镜像遗留文件进入新站点。独立应用继续使用数据库中的 Dockerfile 模板。

流水线持久化 `deploymentProgress`：`preparing`（资源准备）、`submitting`（即将提交、结果可能未确认）、`submitted`（API 已接受更新）、`completed`（指定镜像滚动完成、应用已就绪）。阶段错误会附带最后进度和线上状态说明。镜像推送后记录构建成功；部署中失败不会再因 AfterImage 尚未采集而被标成“构建失败、部署跳过”。滚动完成后版本采集失败仍保留部署成功状态，采集错误保存为独立提示。

这些检查出现错误时停止当前任务后续步骤，其他部署任务继续，不自动回滚。停止流水线不能撤销已提交的 Kubernetes 更新。数据库最终状态写入失败会明确报告，不发送普通完成通知；中断或结果不确定时应按日志和集群实际状态处理，不承诺通用断点续跑。

制品重复提交按第 2 节的“一份制品只更新一次”规则处理。浏览器旧资源兼容由业务开发负责，本项目不增加资源保留机制；不增加异常旧目录的专用恢复流程。

## 16. 批次失败处理边界

一次选中 10 个制品不一定产生 10 个部署任务：Java 服务与 web-cdr／web-opm 各自独立，web-main 和所选子应用合并为一个任务。跳过失败按实际部署任务处理，不在一个失败的 web-main 组里继续制作缺少部分所选子应用的新镜像。

错误归因依据实际日志：制品准备、构建命令、推送和 Kubernetes API 的原始错误用于定位更新工具、模板或环境问题；启动异常需要结合容器日志、配置与探针判断是否为应用代码问题。仅有 CrashLoopBackOff 不能自动判定为业务代码 bug。平台不判断计费和业务流程是否正确。

## 17. 更新与回滚完成标准

只制作、推送并部署本次唯一镜像 tag。指定镜像滚动更新完成、应用就绪即部署完成。回滚由人员触发，恢复记录的旧镜像并等待滚动完成；版本信息读取失败或版本值差异不影响两者的成功状态。

Java 的 app.sh、delete_app.sh 模板必须存在且非空；写入失败返回具体脚本路径和原始错误，成功写入才打印已生成。当前任务失败不阻止其他任务继续。

版本采集提示与执行错误分别展示。数据库无法保存流水线最终结果时，服务端记录原始错误，向当前订阅的详情页发送 state_error，停止普通成功／失败完成通知；不会因此自动回滚，也不会自动重放更新。刷新后的历史状态仍取决于数据库中已保存的记录。

## 18. 连接与配置读取错误

Docker 连接检查使用任务上下文，并设 10 秒上限；取消任务或任务超时会中止连接等待。模板需要 `${nodeIP}` 时，节点查询同样使用任务上下文和 10 秒上限，失败会返回具体错误。

Kubernetes 模板中的镜像仓库、SkyWalking 配置，以及 kubeconfig、默认 namespace 的读取，区分“未配置”和“读取失败”。可选配置未配置时保留默认行为；数据库读取失败时返回配置项名称和错误原因，停止当前目标，不用空值或默认环境掩盖读取故障。模板未引用的可选配置不读取。
