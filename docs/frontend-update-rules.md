# 前端主应用子应用与独立应用更新规则

规则版本：1.0。适用系统：df-build-system。适用入口：本地源码任务、离线制品更新、镜像发布与人工回滚。

本规则以 2026-10-15 在 192.168.1.150 上核对的旧发布脚本、prod 集群容器目录及当前项目代码为依据，规定后续实现和验收的目标行为。规则制定后已开展代码实现；实际支持范围、验证证据和仍未提供的能力见[实施与验收记录](frontend-update-implementation.md)。下文保留完整目标约定，不能把全部目标理解为已经上线。

核心约定：主应用和子应用按明确目录更新，共用 web-main 发布目标；独立应用各自发布。未选择的区域保持不变。正常更新保留旧客户端需要的静态资源，回滚必须核对当前发布版本。

## 已核实的线上结构

web-main、web-cdr、web-opm 都以 `/usr/share/nginx/html` 为站点根目录，分别运行在自己的 Deployment 中。三者都是一个副本，采用 RollingUpdate，maxSurge 和 maxUnavailable 均为 25%。站点目录没有挂载共享存储；Nginx 配置挂载在 `/etc/nginx/conf.d/`。一个副本的滚动更新也可能出现新旧 Pod 同时承接请求。

```text
web-main 容器
/usr/share/nginx/html/
├── index.html、config.json、menulist.json
├── js/、css/、assets/、fonts/、img/、cmaps/
├── report-sdk/、reportView.html、grhtml5.js
└── apps/
    ├── 00/、04/、05/……99/、gymk/   业务子应用
    ├── 60/                       当前为空目录
    └── cdn/                      第三方公共静态资源

web-cdr 容器                    web-opm 容器
/usr/share/nginx/html/          /usr/share/nginx/html/
├── index.html                  ├── index.html
├── config.json                 ├── js/、css/、fonts/、img/
└── js/、css/等                 └── 当前没有 config.json
```

现场快照中的 web-main 约 814 MiB，apps/cdn 约 109 MiB。应用配置有 1 个启用主应用、28 个启用子应用、2 个启用独立应用；28 个子应用目录中有 27 个存在入口，60 为空。没有重复 appCode。web-biaodanbjq、web-liuguanhsz 角色未完整确定，保持停用。

主应用 config.json 没有 xiTongId；gymk 的 config.json 也没有 xiTongId；web-cdr 有 xiTongId=cdr；web-opm 没有 config.json。版本文件格式应按应用兼容，不能全局强制一种格式。web-main 镜像时间晚于主目录版本日期是正常现象：后续只更新子应用也会产生一个新的共享镜像。

旧代码的有效规则来自 `/opt/deploy/build_vue_img.py` 和 `asset_publish.py`：主应用排除 apps；子应用写入指定编号目录；web-cdn 单独写入 apps/cdn 且不要求入口；web-cdr、web-opm 单独制作镜像。资源发布保留最近 30 天的历史文件，且至少保留两个历史版本。`publish_vue.py` 和历史 `deploy-vue.sh` 中直接提交镜像、固定 sleep 或部分错误目标等行为不作为新系统的成功标准。

现场证据见 [只读检查快照](../output/frontend-rules-20261015/inspection.json)。原始脚本、Nginx 配置和版本文件保存在 150 的受保护目录 `/opt/df-build-server/pilot-tests/frontend-rules-full-20261015/`，不将凭据或完整业务配置提交到仓库。

## 应用分类与目录归属

| 类别 | 标准制品 | 内容范围 | 镜像与 Deployment | 更新单位 |
|---|---|---|---|---|
| 主应用 main | web-main.zip | 根目录中受管的主应用文件，排除整个 apps | web-main | 主应用区域 |
| 子应用 sub | appCode.zip，例如 04.zip | apps/appCode 内的一个业务应用 | web-main | 指定子应用区域 |
| 独立应用 standalone | web-cdr.zip、web-opm.zip | 各自站点根目录 | 与应用同名 | 指定独立站点 |
| 公共资源 | web-cdn.zip | apps/cdn 内的版本化资源 | web-main | 显式选择的资源文件和版本目录 |

公共资源是共享发布目标的附属内容，不冒充具有 index.html 的业务子应用，也不创建 web-cdn Deployment。00 是有入口的业务子应用，与 cdn 不混用。

应用角色、appCode、制品名、发布目标来自应用注册信息。仅 web-main 可以登记为当前共享体系的 main；sub 的 appCode 唯一、按字符串处理，保留 00、04 等前导零，也支持 gymk。禁止根据 ZIP 内容、分支名称或数字转换猜测目标。停用应用不可匹配为可更新目标，也不能绕过页面直接提交执行。

已有发布历史的应用修改角色或 appCode，需要进行专门的配置迁移和目录归属核对；普通编辑不能悄悄改变历史发布目标。新增子应用先登记目录、制品名、资源前缀、版本识别方式与必要的入口配置，再参与更新。

## 新增子应用

标准流程是“登记应用 → 准备制品 → 预检查 → 发布到现有 web-main → 验证业务接入”。新增子应用使用同一更新入口，不要求修改发布脚本的应用列表，也不要求手工进入容器创建目录。

以尚未使用的编号 42 为例，下列值仅用于说明，本次没有实际创建应用：

| 登记项 | 示例或规则 |
|---|---|
| 应用名称 | web-example，必须唯一 |
| 项目类型 | Vue |
| 应用角色 | 子应用 sub |
| 应用编号 | 42，作为字符串保存，唯一且符合目录规范 |
| 制品名称 | 自动生成 42.zip，与 appCode 绑定 |
| 发布路径 | 自动推导 apps/42，不能任意填写覆盖别的目录 |
| 发布目标 | 使用当前目标环境的 web-main，不创建独立 Deployment、Service 或 NodePort |
| 来源配置 | 源码任务填写真实 Git 仓库，选择正确分支和公共编译配置；纯制品更新不应强制提供 Git |

纯制品更新在登记后进入“新增更新任务”，上传并匹配 42.zip；需要拉取代码编译时，还要另行创建关联该应用的源码任务。保存应用本身不会自动创建源码任务，也不会触发构建或部署。

编号登记前检查应用目录和线上目录归属。cdn 为公共资源保留名，不能登记成普通 sub；已有 appCode 或同名线上目录不能被另一个新应用占用。线上已有目录但平台未登记时，按“接管现有子应用”核对身份、来源和清单，不能冒充首次新增后覆盖。

发布 42.zip 时，包内提供自身 index.html、脚本和样式，资源路径对应 `/apps/42/`。若存在 xiTongId，应为 42；缺少字段的遗留包按已登记的兼容方式核对。所需 CDN 依赖提前存在，或显式纳入同一共享发布计划。

若 web-main 已存在且基线可信，在本地组装输出中自动创建 apps/42，保留主应用、所有原子应用和公共资源，再按共享镜像发布规则执行。无需先部署一个空目录，也无需为 42 创建独立 Kubernetes 资源。若整个 web-main 尚不存在，则先执行包含主应用的首次安装，不能只用一个子包创建共享站点。

### 平台登记与业务接入

df-build-system 的应用配置负责制品身份、构建和部署目标，不等同于业务门户的微前端注册、菜单、权限、租户开通或后端接口配置。保存应用信息不会自动向这些业务系统写入记录。

如果主应用已经通过动态配置或后端服务发现子应用，且新编号的加载路由已支持，新增包发布后只需完成相应业务配置，无需重新编译主应用。如果主应用写死了子应用列表、菜单、路由或存在新版本加载协议，则需要同时更新对应主应用配置或主包，并在同一计划中明确关联范围。不能一概要求每次新增都重编主应用，也不能承诺仅上传 ZIP 就自动出现在业务菜单。

Nginx 必须正确支持新编号的入口和深层页面路由；采用覆盖全部已登记编号的通用规则时，无需每新增一个应用手工改一次 Nginx。新应用若需要额外代理地址、域名或后端服务，将其作为明确依赖配置，不从子包内自动覆盖共享 Nginx。

新增完成应分别验证：应用登记和制品匹配正确、文件和入口已发布、业务门户能按预期加载、授权用户可见并可访问必要接口。页面可直接打开但没有菜单或权限时，应记录“制品已发布，业务接入未完成”，不能把应用保存成功等同于已上线。接入验证使用该应用声明的入口，不在本次规则制定中执行实际业务写操作。

### 当前可行性与待补能力

现有匹配代码从应用配置读取 appCode，组装代码允许目标子目录原先不存在；隔离用例已验证新建 apps/42 时保留主入口、原 apps/04 和输入基线。这个用例只证明目录新增机制，不代表 150 已完成新增子应用的真实发布验收。

规则制定时的旧版本存在 cdn、空 60 的基线阻断、编号及目录归属检查不足、应用表单强制 Git 等问题。本轮实现已覆盖这些代码问题；线上激活与验收状态见实施记录。业务门户的动态发现机制需要按具体新应用核对，平台不能替代其接入配置。

## 主应用更新

常规主应用更新只更新主目录。源码打包明确排除 dist/apps；离线 web-main.zip 包含任何 apps 内容时，预检查拒绝常规更新，提示拆包或使用下述整包更新。禁止仅凭子目录有 index.html 就自动扩大更新范围。

新入口和当前资源集以本次主包为准；同名入口、受管配置和页面文件采用新内容。旧哈希资源按保留规则处理。apps 下的全部内容，包括 cdn、60 和未登记目录，都不属于主应用常规替换范围。

report-sdk、reportView.html、grhtml5.js、menulist.json 等属于需要明确登记的主目录内容。首次接管时，线上已有但归属清单未记录的文件保留并列入差异，不因新包未携带而直接删除。受管的非历史资源文件只有出现在明确删除清单中才删除，删除前检查引用。基础 Nginx 镜像自带的文件不能自动混入最终清单。

常规更新主应用 M1 到 M2，应得到 `M2 + 全部原子应用 + 原公共资源`。主应用版本变化不强制所有子应用版本同步变化，但所声明的主子应用接口及资源依赖必须兼容。

## 子应用更新

04.zip 只允许改变 apps/04 中该应用的当前内容及其历史资源；不更新主目录、其他子应用、cdn 或 Nginx 配置。单包解压后是子应用自身的站点根目录，不应再套 apps/04。旧文件的删除和历史资源保留遵守下文统一规则，禁止清空目录后丢弃全部旧资源。

同一发布批次选择 04、10、12 时，先全部校验，再基于同一份可信 web-main 基线组装一个共享发布目标。任一所选包无效，整个共享目标停止，不发布缺少部分所选应用的镜像。其他独立 Deployment 按各自结果执行。

未选择的子应用、公共资源、空目录和未知文件均应保留，发布前后比较其内容摘要。未选择的 60 没有入口，不能阻止更新 04；若本次选择更新 60，则新 60.zip 必须通过完整业务入口与资源检查。

更新一个子应用无需重新编译主应用，但会制作新的共享镜像并替换 web-main Pod。界面、日志和回滚提示应表达这个实际影响范围。公共 Nginx、主应用和其他子应用仍共享运行进程与资源，不承诺子目录级的独立可用性。

源码任务单独执行时按一次发布处理；多个独立触发的源码任务不被默认为同一个批次。需要几个前端版本一起生效时，应先编译并固定全部制品，再创建一个组合发布计划。

## 独立应用更新

web-cdr 和 web-opm 分别使用自己的源码、制品、基线、镜像和 Deployment。它们不能读取 web-main 基线、写入 apps 或使用 web-main 的 ConfigMap。两者之间也不共享发布锁和回滚版本。

独立应用同样需要输入哈希、可信基线、资源保留、镜像防过期检查及发布后资源验证，不能只因走标准 Dockerfile 分支就减少保护。新的独立站点从自己的有效制品初始化，已有站点从自己的可信基线组装。

旧脚本中 web-cdr、web-opm 使用 `npm run build`；主应用和普通子应用使用 `npm run build:new`。当前应用配置中相应覆盖应保留，安装命令、产物目录和工具版本由实际编译配置控制，不为所有 Vue 项目强行使用同一构建命令。

## 公共资源与整包更新

### 公共资源

CDN 的源码任务读取仓库中的 cdn 目录，沿用旧脚本跳过 Vue 编译的方式；若将来需要预处理，应由该资源任务明确配置。web-cdn.zip 规范化后的内容限定在 cdn 资源根目录，清单映射到 apps/cdn。它必须显式选择，不能因为主包顺带携带就进入发布。公共资源不要求 index.html，但要求有文件清单、校验和及依赖范围。

第三方库优先沿用现场已经存在的 `库名/版本号/文件` 形式。新增版本目录，保留现有版本目录；相同 URL 路径已有内容发生变化时拒绝普通更新，改用新版本路径。删除库版本必须确认当前应用、保留历史入口和可回滚版本都不再引用，不能按本次 ZIP 缺少该目录判断可删除。

业务子应用引用的新 CDN 文件必须在其入口切换前可用。只更新 04 时不强制重新上传 CDN；只有存在明确新增依赖时才加入同一共享发布计划。

### 整包更新

整包用于明确联合发布或首次安装，必须提供列出主应用、子应用和公共资源的发布清单。预览逐项展示实际更新区域及前后版本，不以“一个 web-main.zip”掩盖全部影响范围。

普通模式禁止主包包含 apps；整包模式可以包含完整的 apps/appCode 及 apps/cdn，但每项必须列入清单并通过对应类型校验。内嵌包和独立 ZIP 同时提供同一个区域时直接拒绝，不设置隐含覆盖优先级。未知目录、不完整子应用和清单外内容不能被自动启用。

整包联合更新也只更新清单中的区域，缺少某个线上子应用不代表卸载。卸载子应用或重建整个环境属于单独操作，必须明确列出删除对象与依赖。

## 输入制品与版本校验

源码和离线制品在进入镜像制作前使用同一校验流程。源码在本地环境编译；客户环境不拉 Git、不临时安装依赖或编译用户上传的 ZIP。

1. 固定来源、应用身份、角色、appCode、制品名、大小和 SHA256；离线制品没有 Git 信息时不伪造 commit。源码记录实际仓库、分支、完整 commit 和编译配置快照。
2. 主应用、子应用及独立应用接受包根目录 index.html 或单一顶层 dist/index.html 两种结构；同时存在两套入口等歧义包拒绝。文件名使用标准小写 .zip 和已登记的应用名或 appCode；上传目录可以嵌套，但同名不同来源不得被静默覆盖。
3. 完整读取压缩包并检查校验和，检查路径穿越、绝对路径、符号链接、重复解压路径及压缩展开大小和磁盘空间。不能仅打开第一个 ZIP 项就称为完整校验通过。
4. index.html 必须是普通文件，并包含有效应用脚本。按 HTML 语法解析引用，支持单双引号和合法的无引号属性；校验本地脚本、样式和构建清单中的延迟资源存在且落在允许范围。静态请求不能依赖 SPA 回退伪装成成功。
5. main 资源前缀为根路径；sub 为 `/apps/appCode/`；cdr 兼容其现有相对路径，opm 兼容其现有根路径。公共依赖 `/apps/cdn/` 必须单独解析。不能把“所有引用都以当前前缀开头”作为唯一标准；声明的共享依赖需在最终站点中存在。
6. config.json 存在且含 xiTongId 时必须与登记的身份匹配，不能将 10 的包改名为 04.zip 通过。主应用不要求 xiTongId，cdr 对应 cdr，gymk 兼容既有缺失字段，opm 兼容没有 config.json。
7. 每个发布区域都记录文件清单和 SHA256 作为最低可验证身份。已有 config.json 的业务版本一并记录；没有版本文件的遗留包，以明确的应用绑定、固定制品哈希和文件清单验证，不为它注入可能影响运行的假 config.json。新的源码制品输出独立的构建清单，逐步补齐提交来源。
8. version、date、branch 不是自动判定新旧的排序键。现场日期格式不统一，多个子应用的 version 常相同；以发布序列、源码提交和内容哈希区分版本。版本降低只在显式回退计划中出现。
9. 文件预检查完成后再登记该目标的制品使用记录。同一上传版本中的文件只允许提交一次，重复请求不能重复创建发布。输入无效不占用；已提交后即使后续失败、取消或回滚，也需重新上传创建新更新，不能通过原地换包清除历史。

## 基线与组装

已有目标优先从当前已稳定运行的指定镜像读取完整基线，不能使用旧 Jenkins 工作区、某个最新上传目录或镜像 latest 作为默认基线。Pod 导出必须核对 Deployment、ReplicaSet、容器归属、期望镜像和 Ready 状态，检查传输、解压结果与来源在导出前后是否变化。

快照记录集群标识、namespace、Deployment UID、generation、resourceVersion、镜像引用及 digest、各区域文件摘要、ConfigMap 版本和预期发布范围。镜像推送后和每次提交集群变化前重新核对，冲突时停止并要求重新基于当前版本组装。独立应用与共享目标均执行这项检查。

业务入口校验只针对主入口和本次所选业务区域；保留区域完整复制并校验摘要。cdn 按公共资源规则检查，60 这样的未选择空目录原样保留。共享基线损坏、权限或网络错误不能被当作“首次部署”。主入口损坏而无法取得可信运行基线时，进入明确的修复发布流程，使用可验证的历史镜像或完整恢复清单，不能空目录拼装。

所有组装只发生在隔离工作区，输入、导出基线与输出目录分开；不向运行中的容器直接覆盖文件，不对生产目录执行 rm，不将中途复制结果作为成品。生产容器站点没有共享存储，不能假设在某个 Pod 写入文件会自动同步其他 Pod。

首次安装仅在目标明确不存在时执行。web-main 至少包含有效主应用，以及该环境声明必装和主入口引用的子应用或公共资源；不要求安装全局登记的全部 28 个子应用。独立应用各自初始化。已有资源先核对，不自动删除同名 Deployment、Service 或 ConfigMap。没有旧入口的首次安装直接发布完整正式镜像，不构造不存在的旧入口准备阶段。

## 静态资源保留与滚动发布

### 文件生命周期

入口 HTML、受管运行配置等可变文件使用本次版本。带内容哈希或版本目录的静态文件保持同一路径同一内容；本次增加新文件，并保留旧入口、旧运行页面可能继续请求的资源。

保留窗口沿用旧发布器的规则：退出当前版本后至少 30 天，且至少保留两个历史版本，两者取覆盖范围的并集；当前版本和允许回滚版本引用的资源始终保留。状态和文件摘要按应用区域持久保存，不依赖可清理的临时工作区。首次接管无法证明归属和年龄的旧文件先保留登记。

同名 JS/CSS 或公共 SDK 内容变化不能靠覆盖和刷新缓存解决。主目录已有 grhtml5.js、report-sdk/sight-report-embed.js 等固定路径；内容不变可保留，内容变化时采用新文件名或版本目录并更新引用。仅改变 `?v=` 而服务器仍以同一个文件响应所有版本，不能视为已经支持旧版本并存。

更新过程中不顺带清理未选区域。垃圾回收作为有明确范围的独立维护计划，取得同一目标锁并记录结果。垃圾回收只删除超过保留范围、无当前或回滚引用、且哈希仍匹配已登记旧资源的文件。未知文件、内容被外部改变的文件、保留区域和 CDN 版本不盲删。空间不足时在发布前停止并报告，不自动缩短保留期限；镜像仓库同时保留有效回滚镜像和对应清单。

### 新旧 Pod 同时服务

只在新镜像中保留旧文件，能照顾旧页面，却不能解决“新页面请求被分到还没有新 JS 的旧 Pod”。当前站点资源都在各自镜像中，不能把一次普通滚动更新宣传为浏览器资源无中断。

在现有部署结构下，目标实现采用一条业务流水线内的两阶段发布：

| 阶段 | 业务入口与固定配置 | 静态资源 | 完成条件 |
|---|---|---|---|
| 资源准备镜像 C | 保留基线 B 的入口和固定配置 | B 的全部内容加上本次新增的不可变资源 | 所有目标副本稳定运行 C，资源验证通过 |
| 正式镜像 F | 切换本次所选区域的入口和配置 | 保留 C 的新旧资源集合，按清单处理当前内容 | 所有目标副本稳定运行 F，区域及 HTTP 验证通过 |

源码编译、离线匹配和两个镜像的制作可以提前完成。镜像仅制作模式不改变 Deployment；实际发布阶段才依次部署 C、F。资源准备与正式发布是两个技术动作，界面仍表现为同一个目标更新任务，不要求用户重复选择制品。

仅增加公共资源、业务入口与固定配置完全不变的计划，可将资源镜像作为该计划的最终镜像，不做无意义的第二次滚动。

C 阶段不修改旧入口引用的可变资源。固定路径运行配置在 F 滚动期间也必须能被新旧客户端共同识别；不兼容变更使用版本化配置或明确维护窗口。不能并存的同路径变更应先改为版本化资源；尚不能满足并存要求的应用，必须在计划中明确使用有维护窗口的切换方式，不能默认零中断。今后改用独立静态资源服务时，可以替代 C 阶段，但要通过等价的资源可用性验收。

B、C、F 的 digest 和阶段分别记录。C 已部署就是线上已发生镜像变化，状态不得显示“尚未提交”；F 之前检测到外部变化则停止。检查时认可本任务已经登记的 B→C→F 转换，禁止把任何不同镜像都当作自己的准备结果。

## 镜像发布与环境配置

所有前端目标的发布锁以集群、namespace、Deployment 为键；共享主应用、子应用、CDN、回滚和修复操作使用同一把目标锁。独立应用各自锁定。当前单实例的进程锁只适用于单后端，多实例部署前必须有跨实例互斥。提交更新继续使用 Kubernetes resourceVersion 防止覆盖其他操作者的修改。

本地环境保留既有行为：完整校验和镜像推送成功后自动继续发布；非本地环境先停在镜像就绪，用户提交后使用同一份输入和镜像发布。显式“仅制作镜像”始终不部署。手动发布时基线过期要重新组装，不能跳过检查或把旧镜像当作最新补丁。

当前生产应用镜像路径为 `registry/prod/目标应用`，基础镜像为 `registry/base/nginx:v1`；仓库主机用于认证，不将项目路径混入仓库主机。更换项目路径属于明确的环境迁移。

正式源码镜像 F 保留项目现有分支、commit8、北京时间戳命名约定；资源准备镜像 C 使用不同的唯一标签，例如正式标签加 assets 后缀，并共同记录为一次发布。两个阶段不能复用并覆盖同一标签。制品组合涉及多个仓库时使用发布 ID，不将一个子应用提交号冒充整个 web-main 的版本。统一记录仓库确认的 digest，并校验 tag 对应内容未改变；生产目标优先使用 digest，不使用 latest 或可被随意覆盖的辅助标签。

常规代码更新只改变目标镜像，不隐式覆盖线上 Nginx、Service、Ingress、端口、挂载、探针、副本和业务连接参数。配置确需变更时，在同一计划中独立列出差异、保存旧对象并验证，恢复时一并处理。现有 Nginx 配置引用的 API、报表及其他代理路由必须保留。

config.json 中业务版本随制品更新；环境相关字段按登记的字段来源合成，未登记字段不得猜测保留或覆盖。现场存在 homePath、position 等业务字段，不能把所有 JSON 都归为环境配置而导致新版本永远不生效。密码和连接凭据不写入制品、公开清单或日志。

## 路由缓存与发布成功标准

主应用根路由回退主入口；已登记子应用的页面路由回退自己的 apps/appCode/index.html，gymk 与数字编号同等支持。CDN 和静态资源路径不做 SPA 回退。独立应用页面路由回退自己的入口，但不存在的 .js、.css 等必须返回 404，不能返回 200 HTML。

全部入口 HTML 和可变运行配置不使用长期缓存，响应要允许及时取得当前入口；含内容哈希或版本路径的静态资源可保留现场的 7 天缓存。对 404 静态响应不设置七天公共缓存，避免旧错误在资源补齐后仍被保留。以实际 HTTP 响应为准；磁盘上的 ConfigMap 或 nginx -T 输出不证明工作进程已经加载新配置。

某个发布目标成功需要同时满足：

1. 输入、清单、镜像和目标匹配，推送后的 digest 可确认。
2. 所有目标副本运行预期最终镜像，controller 已观察到目标 generation，Ready、Available 等数量满足期望，无未完成的新旧版本混合。
3. 主入口和所选业务入口返回正确页面；本地脚本和样式返回正确类型及内容，不以 HTML 回退冒充资源成功；子应用深层路由落到正确入口。
4. 新增 CDN 依赖可访问；保留的旧哈希资源仍可读取。组装清单与所选区域实际文件匹配，未选区域摘要不变；多副本不能仅检查任意一个 Pod 就判定全部正确。
5. 能取得业务版本时与本次清单核对；不支持业务版本文件的遗留应用使用文件清单和构建来源验证。缺少可选展示字段与文件内容校验失败分别记录。
6. 部署事实及每区域前后版本成功持久化。镜像实际已发布但记录失败时，单独显示“已发布，记录异常”，不能伪称旧版本仍在线。

平台的技术校验不代替业务页面、登录和核心功能验收。涉及主子应用接口兼容、报表 SDK、业务配置或后端协议变化的批次，还需要对应的业务验证结果。不能仅凭 Nginx 的 /index.html 探针成功就声称业务正常。

## 失败取消与重试

| 边界 | 规则 |
|---|---|
| 输入、组装、构建、推送失败 | 停止当前目标；不提交其集群更新；同批其他独立目标可继续 |
| 共享组中一个所选子包失败 | 整个 web-main 组停止，不少包发布 |
| C 已发布而 F 尚未提交 | 业务入口仍为 B，记录资源准备已生效；后续操作先核对当前镜像与阶段 |
| Deployment 请求超时或响应丢失 | 标记结果待核对；读取真实镜像、generation 和副本，不据客户端错误推断线上未变 |
| F 滚动中失败 | 保留已提交进度和故障证据，不自动回滚；其他 Deployment 的结果独立保留 |
| 浏览器断线或关闭 | 不取消后台任务；重新打开可查询同一任务 |
| 取消已提交的任务 | 停止后续动作或等待，不撤销 Kubernetes 已接受的更新 |
| 后端重启 | 不盲目重放集群写入；依据持久化阶段和实际镜像核对，不能把 C 或 F 当作未开始 |
| 基线冲突或修复后重试 | 基于当前可信状态创建新计划；保持原失败历史，不原地换包伪造原任务成功 |

一个批次包含三个 Deployment 时，按三个目标展示结果。部分成功不能报全部成功，失败也不自动撤销已经成功的其他应用；需要业务上同时切换的对象应在计划中明确依赖和执行顺序。

## 回滚与定向回退

### 回滚最近一次共享发布

web-main 的镜像回滚范围包括主应用、全部子应用和 CDN，即使原任务只更新了 04。执行前展示完整范围，核对当前镜像及发布序列确实对应待回滚批次的 F，或该批次已提交并登记的 C。若其后已有其他发布，旧批次回滚拒绝执行，不能覆盖后来更新。

两阶段发布保存 B 为更新前业务基线，并保存 C 作为含新旧资源且仍使用旧入口的兼容恢复镜像。恢复时优先采用经验证的兼容恢复版本，使已经打开新页面的客户端仍能请求其资源。恢复涉及的版本化配置快照一并核对；不能仅恢复镜像却宣称已恢复整个配置环境。

若紧急情况下只能恢复历史 B 的原 digest，应明确标记其旧客户端资源兼容限制。恢复完成后仍检查入口、资源及所有目标副本；不自动回滚数据库、业务数据或其他 Deployment，也不自动清理首次安装产生的资源。

### 只回退一个子应用

“把 04 回退到上一个业务版本，同时保留后来更新的 10”应创建新的定向回退计划：读取最新 web-main 基线，只替换 apps/04 的受管当前内容，保留其他区域及资源窗口，再走完整制作和发布流程。不能调用旧批次的整镜像回滚来实现此操作。

独立应用只回退自己的发布目标，但同样检查是否已有较新的发布。回滚失败保留实际已完成的目标和原始错误；不因为一组失败自动撤销另一组已经完成的回滚。

## 发布记录与界面要求

文件清单分别记录当前版本文件集、历史保留资源集和明确删除集；验证服务目录时按这三类内容核对，不把合法保留的旧资源误报为 ZIP 之外的脏文件。

发布计划固定环境、输入哈希、角色、appCode、目录范围、依赖、预期基线、镜像 digest 和配置差异。页面按逻辑目标展示：web-main 共享组、web-cdr、web-opm；共享组展开每个实际更新区域及保留区域。

主包内嵌子应用和 CDN 在整包模式中逐项记录，不只给外层 ZIP 一条记录。对每个区域保存更新前后文件摘要、业务版本或来源信息；共享镜像版本与主应用业务版本分别显示。未选区域、资源保留、删除清单、失败阶段、C/F 进度和回滚范围均可追溯。

普通页面保持简洁，详细文件操作、校验差异与原始错误放在对应流水线阶段和发布明细中。不把堆栈、配置凭据和长日志平铺在页面顶部。

## 当前实现差异与实施顺序

当前实现说明见 [现有 Vue 构建与更新流程](vue-app-build-flow.md)。下表记录规则制定时的差异和实施顺序；本轮进展及尚未覆盖部分以实施记录为准。

| 顺序 | 当前差异 | 需要达到的行为 |
|---|---|---|
| P0 | webChildren 对基线 apps 下每个目录强制 index，现场 cdn 和空 60 会阻断共享更新 | 按归属和本次范围校验，公共资源及未选空目录保留 |
| P0 | 主包内完整 apps 目录自动扩大范围；源码打包没有排除 apps | 常规主包排除 apps；整包模式显式清单与逐项预览 |
| P0 | 独立应用缺少共享流程已有的输入与过期基线保护；应用编辑及制品执行约束不完整 | 三类应用统一身份、哈希、停用和目标检查 |
| P0 | 目标目录清空替换，旧资源保留策略未迁移 | 接管旧清单，保留资源，检查同路径内容冲突与删除范围 |
| P0 | 历史批次回滚不检查是否已有后续发布 | 回滚检查当前镜像与发布序列，区分整镜像回滚和定向回退 |
| P1 | 当前只制作一份正式镜像，未实现 C/F 两阶段 | 资源先可用、入口后切换，兼容恢复镜像与阶段记录齐全 |
| P1 | 子应用探测深层 URL 返回主入口；独立站点缺失 JS 返回 200 HTML | 正确页面回退与静态 404；缓存策略按实际响应验收 |
| P1 | 当前滚动成功后业务版本只采集展示，未执行全副本文件清单与资源验证 | 强制技术完整性验证，兼容缺失版本文件的遗留包 |
| P1 | CDN 缺少专门输入类别；内嵌子应用没有逐区域部署记录 | 公共资源发布和区域记录完整，不伪装为普通 sub |
| P2 | 锁只在单进程内，资源寿命及版本化配置没有完整模型 | 多实例互斥、受控回收、配置快照与容量管理 |

先修复确定的阻断与范围保护，再在隔离环境验证资源兼容发布和回滚，最后验证真实集群。P0 完成不等于已具备浏览器资源无中断能力。

## 验收用例

以下是实现后的验收要求；本次只读检查和既有隔离复现不等于这些用例全部通过。

| 场景 | 必须满足的结果 |
|---|---|
| 在应用配置登记新的 42，再提交 42.zip | 自动匹配并在输出创建 apps/42，保留主应用、所有既有子应用及 CDN，无需预建容器目录 |
| 新编号重复、使用 cdn 保留名或占用未知目录 | 提交前拒绝；既有目录只能经过明确接管处理 |
| 新子应用已发布但业务菜单或权限未配置 | 分别展示部署与业务接入结果，不伪称已经在门户可用 |
| 主应用采用动态发现或写死应用列表 | 前者无需重编主包，后者明确关联主应用配置或主包更新，分别验收 |
| 只更新 web-main | apps 全树摘要不变，主包混入 apps 被常规模式拒绝 |
| 只更新 04 | 主应用、其他子应用、cdn、空 60 均保持；当前 04 内容和资源窗口正确 |
| 同时更新 04、10、12 | 同一共享发布计划，三包全部预检查；其中一包失败则不发布共享组 |
| 主包内嵌 04 并另选 04.zip | 拒绝重复来源，不自动选择优先级 |
| 更新 cdn 的一个库版本 | 新版本可用，既有版本及其他区域不变；不要求入口 |
| 更新空目录对应的 60 | 无有效 60.zip 时拒绝该目标；不影响未选择 60 的普通更新 |
| 10 的包改名为 04.zip | 包含的身份与 appCode 冲突时拒绝 |
| gymk 不含 xiTongId | 明确绑定及文件清单可验证时接受，不人为注入字段 |
| opm 不含 config.json | 使用其构建和文件清单验证，不因为缺少可选文件拒绝合法包 |
| 同一 hash 路径内容变化 | 拒绝覆盖，要求新资源路径 |
| 老页面在更新后加载旧 chunk | 资源窗口内继续获得原内容 |
| 新页面请求落到旧副本 | C 阶段保证各副本已有新资源，不出现新 chunk 404 |
| 子应用深层 URL 与缺失 JS | 页面返回对应子应用入口；缺失 JS/CSS 返回 404，不能是 200 HTML |
| 手动发布前更新了其他子应用 | 旧基线任务被拦截，重新组装后才能发布 |
| C 成功、F 失败或响应丢失 | 如实记录已提交状态并核对集群，不虚报完全未变或自动完成 |
| 先更新 04、后更新 10、再回滚较早 04 批次 | 整镜像旧批次回滚被拦截；定向回退 04 后保留当前 10 |
| 单独更新或回滚 cdr | main、子应用、opm 内容和镜像不变 |
| 并发、重复提交、取消和重启 | 同目标串行，无重复发布；已接受的集群变更不被标成未执行 |
| 第一个副本正确、其他副本异常 | 不判定目标发布完成 |
| 未选未知目录和缺失归属的历史文件 | 保留并登记，不因新包缺省而删除 |
| 存储不足或过期资源回收 | 发布前报告容量问题；仅回收满足期限、引用和哈希条件的资源 |
| 实际部署完成但数据库写入失败 | 展示已部署且记录异常，提供镜像及集群事实供恢复 |
