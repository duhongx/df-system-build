# 监控与巡检报告已确认需求

确认日期：2026-10-30。

本文件记录用户逐项澄清后的需求，作为后续开发和验收依据。与旧方案、历史实现说明冲突时，以本文件为准。2026-11-02 已按本文件实施开发；完成范围与本地验证记录见第 8、9 节，部署状态单独说明。

## 1. 使用场景与职责

- 巡检报告用于客户现场节假日、季度等阶段性检查，了解系统各组件的运行情况并存档。
- 报告以真实数据、对象归属和实际采集时间为主，后续由用户提交给 AI 大模型分析和审核。
- 监控中心负责后台持续采集与数据展示；生成报告负责读取、整理和冻结已有数据。打开页面或生成报告不是后台采集的启动条件。
- 本轮不据“后续交给 AI 分析”的使用场景，扩展自动调用大模型、健康评分或自动整改功能。

## 2. 数据保存与查询范围

- **48 小时是监控数据在平台数据库表中的保留期限。** 按此规则清理过期监控记录。
- 存储保留期限不等于业务查询窗口，不代表用户要求统计或查询“近 48 小时慢 SQL”。
- 慢 SQL 默认查询当前仍保留的已有记录，不附加默认时间段筛选，不新增“48 小时慢 SQL 统计”要求。
- 正式报告及其冻结数据独立存档，不随监控记录的 48 小时清理删除；报告读取不能依赖源监控记录继续存在。

## 3. PostgreSQL 范围与慢 SQL

### 数据库范围

- 每个已纳管 PostgreSQL 实例覆盖**所有数据库**，不能只检查连接配置中的默认数据库。
- 保留实例、数据库与检查结果的对应关系；实例级指标与数据库级指标分开汇总，不能混用统计范围。
- 无法读取的数据库或项目如实说明，不能静默遗漏，也不能用其他数据库的结果代替。

### 慢 SQL 来源与展示

- 监控页与报告页展示**已经发生、从 PostgreSQL CSV 日志提取的慢 SQL**。
- 沿用现场 CSV 日志现有的 **5 秒（5000ms）**慢 SQL 标准，不另外设定新的认定规则。
- 当前正在执行的 SQL 会话不能代替上述历史慢 SQL 记录。
- 按**发生时间倒序**展示，由**后端分页查询已有记录**。不能先固定截取最近 50 条，再只在前端对这 50 条分页。
- 记录保留数据库归属、发生时间、耗时及 SQL 等实际信息，供监控展示、报告存档与后续分析使用。
- 在线报告冻结生成时的同一批已有记录，沿用相同排序和分页方式；不因为生成或翻页重新采集数据库日志。

## 4. 报告的数据来源与生成

- 直接汇总监控中心已有的数据并冻结为本次报告快照。
- **生成报告不触发补采，不等待后台巡检或采集任务完成，不为报告临时执行 SSH 命令或组件 API。** 后台采集继续独立运行。
- 分别保留报告生成时间和各项数据的实际采集时间。已有一小时前的数据就如实标注时间，不仅因数据不够新而触发补采。
- 某个项目缺失或读取失败，只说明该项目的实际情况，不能丢弃或覆盖其他已经取得的数据，不能把缺失值补成 0。
- 报告生成状态与数据可用情况分开表达。平台汇总超时不能被包装成服务器权限或部署故障。
- 在线查看报告、下载 PDF；不提供 HTML 下载作为报告使用入口。
- 正文保留有价值的数据；容器运行时重复挂载、冗长清单、长 SQL 等应合理精简或截断，并注明总量和展示范围。不能因正文精简而悄悄丢弃已保存记录。
- 正文不反复铺开 `context deadline exceeded`、无检查项说明的“未取得本项检查结果”，或没有实际依据的“核对权限和部署方式”等通用建议。

## 5. 空间阈值与其他判断

| 项目 | 已确认口径 |
| --- | --- |
| 磁盘/存储容量使用率 | **超过 75%** 提示异常 |
| inode 使用率 | **超过 75%** 提示异常 |
| 其他指标 | 如实呈现运行状态、配置、计数、时间和数据可用情况，不自行扩展健康评分、异常判定或通用整改结论，供后续 AI 分析审核 |

75% 阈值适用于磁盘容量和 inode，不据此扩大到 CPU、内存或 JVM 堆等指标。磁盘容量/inode 表以挂载点为标识，不显示设备路径。

## 6. RabbitMQ

- 正常展示各队列及相关汇总数据，包括队列名称、VHost、消息数量、Ready、Unacked、消费者，以及已有可取得的速率等实际字段。
- 用户曾提出“超过 300 条认为堆积”，随后明确“不需要关注，正常显示就行”。**以最后确认的正常展示要求为准，本轮不增加 300 条堆积判定规则。**
- 不继续围绕单个队列/实例总量、Ready/Ready+Unacked 增加阈值解释或告警规则；这些数据按各自实际含义正常展示。

## 7. 延续的展示要求

- Linux 主机和组件实例通过可搜索的下拉切换，适用于客户现场三十多台主机的情况。
- Linux 复用服务器管理已有监控数据；磁盘容量/inode 仅展示挂载点和容量指标，省略容器运行时重复挂载。
- 组件数据来自已有环境配置、组件连接及后台采集，不要求每次生成报告手工指定服务器上应检查哪些组件。
- SkyWalking 延续主机服务/进程管理入口，提供状态、启动和重启能力，不新增独立监控页面。

## 9. 实现与验证范围

- 创建报告使用平台数据库的一致性事务冻结已有监控快照与日志记录。已冻结的对象状态、日志接入状态及数据时间不随随后连接修改或采集更新变化。后台仅排版生成 HTML 在线正文与 PDF，数据缺口不会把成功生成的报告标成“部分完成”。
- 慢 SQL 完整存档使用独立表 `inspection_slow_queries`；监控源仍按 48 小时保留，主动删除报告时才删除对应存档。报告正文列最近 5 条短摘要并写明总数，在线页按发生时间倒序后端分页，保留完整 SQL、实例和数据库归属。
- PostgreSQL 枚举全部数据库，单独列出不可连接/无权限数据库及原因；复制槽、归档与连接上限等实例数据只采一次。表统计、锁等待、长事务和指导书 SQL 按数据库保存，失败库不会覆盖成功库。
- 缺失项在各组件章节集中成表，保留检查名称、对象、具体原因与时间；正常的业务数据表继续展示。长表、长 SQL 只在正文精简，快照中的数据不截掉。磁盘容量和 inode 严格按 `>75%` 提示异常，CPU/内存不套用此规则。
- 回归场景包括 537 条跨批次慢 SQL 的完整冻结与末页读取、源记录清理后的存档读取、日志接入状态冻结、报告重排不重新采集、多数据库指导书执行与权限隔离、采集锁 SQL NULL 释放、实例切换丢弃延迟响应、75%/75.1% 边界，以及 PDF 表格和分页。
- 验证只使用本地临时 PostgreSQL、HTTP/SSH 测试样本和已有报告存档，不代表已经在客户服务器部署或完成现场验收。

本地验证结果：前端 57 项通过；完整后端 585 个顶层测试、含子测试 924 项通过；重点并发回归 47 项通过（40 个顶层测试）。默认全量测试中 4 项需外部环境或样本的测试跳过，其中历史报告样本排版已另行提供本地存档样本运行并通过，其余真实集群发布/真实 exporter 验证未执行。完整日志位于 `output/selfcheck/20261102T020525Z-83919/`，补充回归、PDF 渲染和构建记录位于 `output/confirmed-monitoring/`。后续版式兼容调整另通过完整 `internal/inspection` 测试。

本轮只完成本地开发与自检，尚未提交推送或更新服务器。客户现场的连接权限、数据覆盖和实际报告效果仍由部署后验收确认。
