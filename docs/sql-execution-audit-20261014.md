## P1：已复现的问题

### 1. 显式事务脚本会把未提交或已回滚的变更记录为成功

位置：[逐条执行与结果保存](../backend/internal/service/sql_file_execution.go#L224)、[重试跳过成功语句](../backend/internal/service/sql_file_execution.go#L206)。

普通文件允许导入并执行 `BEGIN`、`COMMIT`、`ROLLBACK` 等事务控制语句；执行器在每次 `ExecContext` 成功后立即记录 `SUCCESS`，没有等待事务提交。文档约定的逐条自动提交因此不成立。

复现：执行 `BEGIN; UPDATE counter SET value=value+1; ROLLBACK;`，文件与 UPDATE 都记录为成功，但数据库值仍为 0。若事务中途报错或缺少 COMMIT，之前记录成功的修改同样可能被回滚；随后重试会跳过这些实际未生效的语句，造成漏执行。事务里的错误跳过选项也无法消除 PostgreSQL 的事务失败状态。

建议：按当前逐条提交的产品约定，在导入和执行入口明确拒绝顶层事务控制语句，并检查既有文件；若要支持事务脚本，需要按事务组统一确认提交、回滚和重试状态，不能继续逐句提前记成功。不要通过文本匹配误拦截函数体内的 BEGIN/END。

复现用例：`rollback_reported_success`。

### 2. 删除后重新导入可以绕过结果待核实保护，重复执行已提交 SQL

位置：[删除文件](../backend/internal/service/postgresql_service.go#L3521)、[导入只读取未删除记录](../backend/internal/service/postgresql_service.go#L1637)。

执行结果无法保存时，语句会标为 `UNKNOWN`，直接重试和覆盖会被禁止。但文件删除只禁止 `SUCCESS` 和 `RUNNING`，允许删除包含 UNKNOWN 或部分成功语句的失败文件。重新导入同名文件时只查未删除记录，全部语句重新变为待执行，丢失保护依据。

复现：业务 UPDATE 已将计数从 0 改成 1，注入平台结果保存失败后得到 UNKNOWN；直接重试被拒绝。删除、同名重导、再次执行成功，将计数从 1 改成 2。

建议：删除与重导必须共同保留执行历史和未确认结果保护。至少禁止删除含 RUNNING/UNKNOWN 的文件；对已部分执行文件，重导应核对历史并继承执行记录，不能把软删除当成全新脚本。

复现用例：`delete_bypasses_unknown`。

### 3. 执行启动与覆盖操作没有共同锁，可生成两份有效文件并重复执行

位置：[执行前读取文件和语句](../backend/internal/service/postgresql_service.go#L2882)、[启动后保存整个旧文件对象](../backend/internal/service/postgresql_service.go#L2845)、[覆盖导入](../backend/internal/service/postgresql_service.go#L1626)、[运行进度 Save](../backend/internal/service/sql_file_execution.go#L155)。

文件和语句先被读入内存，随后才注册进程内取消表和保存 RUNNING。导入、删除、跳过没有使用这一注册表，也没有共同的数据库行锁或状态条件更新。旧快照通过 GORM `Save` 保存全部字段，能把已被覆盖作废的旧文件 `is_deleted` 改回 false。

复现：在执行准备读取完成处设置同步屏障，先覆盖同名文件，再继续启动执行。旧文件被重新激活，与新文件同时有效；两个文件都可执行相同 UPDATE，计数最终为 2。

建议：在数据库事务中原子领取执行权，并与覆盖、删除、跳过使用相同锁和状态校验；状态更新只更新必要字段并附带当前状态、未删除或执行标识条件。有效文件身份还应有数据库唯一约束。仅在前端禁用按钮或只使用进程内 map 不足以解决。

复现用例：`overwrite_races_execution_start`。

### 4. 视图预检和分析能覆盖执行状态，绕过防重复执行保护

位置：[预检](../backend/internal/service/postgresql_service.go#L678)、[分析及替换备份](../backend/internal/service/postgresql_service.go#L606)、[领取视图任务执行权](../backend/internal/service/postgresql_service.go#L1149)。

执行入口对 EXECUTING/RESTORING 加行锁并拒绝重复提交，但预检、分析没有同样的状态保护。预检可将 EXECUTING 改为 PRECHECK_PASSED，分析可将状态改为 ANALYZED 并删除重建原备份。此后新的执行请求能够再次领取任务。执行入口本身会对非 PRECHECK_PASSED 的状态调用预检，因此重复执行请求也可能触发这一漏洞。

复现：第一次领取任务后，直接再次领取被正确拒绝；调用预检后状态变为 PRECHECK_PASSED，第二次领取成功。该用例复现状态保护失效，没有并发执行真实字段变更。

建议：分析、预检、执行、恢复、单对象操作共用任务状态锁；执行中的任务禁止分析和预检，备份应按执行版本固定。预检完成时要条件更新，避免覆盖期间产生的执行状态。

复现用例：`precheck_overwrites_execution_guard`。

### 5. 视图分步模式没有使用配置的锁等待和语句超时

位置：[分步计划生成](../backend/internal/service/sql_view_dependency.go#L322)、[分步执行](../backend/internal/service/postgresql_service.go#L1030)、[事务模式才添加超时](../backend/internal/service/sql_view_dependency.go#L377)。

默认模式是 STEP。任务记录 LockTimeout、StatementTimeout，预检还提示执行将使用 lock_timeout，但分步计划只包含 DROP、ALTER、恢复 SQL，执行连接没有设置这两个参数，也没有对应的程序执行期限。

复现：配置 `lock_timeout=1s`、`statement_timeout=2s`，在实际分步执行连接中采集到二者均为数据库默认值 `0`。测试库的 0 表示没有这些超时限制；现场是否存在数据库级默认值本轮未验证。

建议：分步模式在专用连接上显式设置并验证超时，执行后恢复会话配置或销毁连接，避免共享连接池污染；使用程序期限作为补充。所有执行方式的页面提示必须与实际参数一致。

复现用例：`step_timeouts_ignored`。

### 6. 视图删除阶段部分成功后失败，没有尝试恢复已删除对象

位置：[分步删除失败直接返回](../backend/internal/service/postgresql_service.go#L1062)、[仅字段变更失败才自动恢复](../backend/internal/service/postgresql_service.go#L1065)。同样问题存在于独立执行辅助函数 `runSQLViewDependencyStepExecution`。

分步执行每条 DROP 单独提交。多个依赖视图中，前面的 DROP 成功、后面的 DROP 因锁、权限或新依赖等问题失败，会直接退出，已经删除的视图保持缺失。

复现：第一个视图成功删除，第二个 DROP 报错，返回的错误显示未尝试恢复；查询第一个视图已不存在。测试用不存在的第二个视图稳定触发错误路径；现场错误条件可以不同。

建议：记录实际成功删除的对象；删除阶段失败时恢复这一子集，按依赖顺序恢复并验证，准确记录恢复失败的对象。不能简单对所有备份重复 CREATE，因为未删除的对象仍然存在。

复现用例：`partial_view_drop_not_restored`。

## P2：代码检查发现，尚未单独动态复现

1. **管理员密码变更后复用旧连接池。** `getDB` 的配置标识只包含 host、port、database、user，不包含密码或凭据版本；旧连接 Ping 成功就继续使用旧池，新建连接仍携带旧密码。可能出现保存并测试成功，但视图工具稍后新连接认证失败。[位置](../backend/internal/service/postgresql_service.go#L127)。应在连接配置或凭据变化时重建连接池，避免记录明文密码。
2. **多条字段修改中途失败后，恢复步骤写到错误记录上。** `runGroup` 使用一个连续 stepIndex。ALTER 组在第一条失败时直接转入恢复组，没有跳过剩余 ALTER 对应的记录；恢复结果可能被写到未执行 ALTER 的记录上，真正的恢复记录仍为待执行。步骤状态写入错误还被忽略。[位置](../backend/internal/service/postgresql_service.go#L1042)。应给各阶段使用固定记录映射，标记未执行步骤，并处理记录保存失败。
3. **视图任务中断缺少状态恢复。** 启动恢复函数只处理普通 SQL 文件和语句；视图 EXECUTING/RESTORING 任务及步骤没有对应的中断标记。另有领取任务后、获取连接或创建变更记录失败就直接返回的路径，未收敛任务状态。[启动恢复](../backend/cmd/server/main.go#L69)、[执行中的早退](../backend/internal/service/postgresql_service.go#L747)。应把未完成任务标为待核实，依据备份、步骤和目标库结果处理，避免宣称回滚成功或自动重放。
